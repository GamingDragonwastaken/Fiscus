## The local suite is now a deterministic gate, and it was not before

Directive item 4. Two separate defects made a full local run non-deterministic, and both were found by reproducing rather than by reasoning:

- **`test/plugins-host.test.ts` had a load-sensitive deadline** (D-154). Its shared fixture allowed 250ms of child startup for tests that spawn a real `node` child. Under twelve concurrent CPU-bound processes it failed on demand — three runs at 2, 4 and 2 failures. Every intermittent full-suite failure previously observed in this program was this file, and each time it had been set aside as "local contention", which was a description and not a diagnosis.
- **Two tests contradicted each other about the repository artifact** (D-155). `test/build-race.test.ts` asserts that an isolated build does not republish this checkout's `dist/cli.js`, defended by a comment claiming nothing else in the suite builds at ROOT. `test/egress-guidance-launcher.test.ts` ran `npm run fiscus`, whose `prefiscus` hook is `npm run build`. Running those two files together failed EVERY time with no artificial load.

Neither fix weakened an assertion; in both cases the behavioural claim was kept and the incidental dependence on the harness schedule was removed. **A full run under six CPU-bound processes is now 1,666 / 1,662 / 0 fail / 4 skipped.** If a future run is red, treat it as a finding rather than as noise — that reflex is what let both of these survive.

**A third instance was observed and is NOT closed.** On one full run this round, `build-race.test.ts`'s "concurrent builds keep the compiled CLI runnable throughout publication" failed after 38 seconds. It passed in isolation immediately afterwards and passed on the next two full runs, and the failure message was not captured before the run scrolled. So there is one observed failure in roughly a dozen full runs and no diagnosis, which by this file's own rule is a finding and not noise.

**It was hunted with output captured, and did not reproduce -- but the hunt caught something else.** Three further full runs were captured to file. `build-race.test.ts` passed in all three, so that failure is still undiagnosed and still open. Run 3 failed for an unrelated reason that IS now diagnosed, and it is not a Fiscus defect: one `node --test` worker died before its file's tests ran with `CompileError: WebAssembly.Module(): Compiling function #352 failed: invalid branch depth: 4096`, thrown from `node:internal/deps/amaro/dist/index` -- Node v24.18.0's own TypeScript type-stripper failing to compile its SWC WebAssembly module under full-parallel load. `test/claim-profile.test.ts` was reported as `'test failed'` with no assertion and three of its tests never ran; the suite reported 1,747 tests where the other two runs reported 1,750. No Fiscus frame appears anywhere in the stack.

**It happened twice more in the same session, in two more shapes, and the count now matters more than the first instance did.** A later full run failed twice at once, both non-Fiscus: `test/billing-cli.test.ts` spawns a real CLI child, that CHILD died with the same amaro WASM compile error in a different function (`not enough arguments on the stack for f64.add`), and the parent test faithfully turned the child's stderr into an assertion message -- so the failure was reported against a billing assertion that never ran. In the same run `test/claim-support.test.ts`'s worker died on a V8 `Fatal error ... unreachable code` with a native stack and no JavaScript frame at all. The immediately following run was clean: 1,769 tests, 1,765 pass, 0 fail, and zero WASM or fatal-error lines. **Three infrastructure faults in six full local runs, in three different shapes; zero on CI across three operating systems in the same period.**

**The machine, measured rather than assumed.** `os.availableParallelism()` is 12 here, so `node --test` runs up to twelve worker processes, each instantiating Node's own SWC WebAssembly type-stripper, while several test files additionally spawn real CLI children that each do the same. 31.8 GB total with 12.9 GB free at the time of measurement.

**The hypothesis, named as a hypothesis, and what would settle it.** Peak memory and JIT pressure from that fan-out is the obvious candidate, and bounding `--test-concurrency` is the obvious lever -- it weakens no assertion. It is still not pulled, and now for a better reason than the count: **it cannot be shown to work.** Runs pass most of the time either way, so a single green bounded run proves nothing, and shipping a knob documented as a remedy would assert something unmeasured. What would settle it is a rate comparison -- N full runs at the default against N at a bounded concurrency, faults counted -- which is roughly an hour of wall clock per arm at three and a half minutes a run, and is a real measurement rather than a guess. Until then the default stands and the faults are recorded here with their exact stacks.

**What this already changes is how a red local run must be read.** A worker killed by an infrastructure fault is reported in exactly the same shape as a failing assertion -- a bare file-level `'test failed'` -- and when the fault is in a spawned child it is reported in the shape of a NAMED assertion in an unrelated subsystem, which is worse. So: before treating a red run as a Fiscus finding, read the captured output for a stack with no Fiscus frame in it. Both of the diagnosed defects above were found because a red run was taken seriously; these three are the reason a red run must also be READ. **Never conclude from a red run alone; never conclude from a green one either.**
